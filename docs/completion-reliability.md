# Reliable maze completions (Sprint 3)

## Contract and atomicity

`POST /maze/start` adds a server-generated UUID `attemptId` to the existing embedded attempt and response. Send that ID with `POST /maze/complete` alongside `subProfileId` and `date` (`YYYY-MM-DD`). Authentication resolves the owning user; lookup is scoped to that user's profile, date, and attempt. IDs are selectors, not credentials. An unknown ID never falls back to the latest attempt.

Completion uses the server's receipt time minus the persisted server start time, including the existing three-second minimum; client times are ignored. The first committed completion stores its exact JSON response (including a reward catalog snapshot, or null) on the attempt. Retries return that response without changing inventory, timestamps, daily progress, or the leaderboard. Deleted or renamed rewards do not change replayed responses. Completed results remain recoverable even if an attempt subsequently expires.

All affected state already lives in one User document. Mongoose optimistic concurrency makes its save a single version-checked atomic MongoDB update: attempt completion, result snapshot, inventory, progress and version commit together. A losing writer reloads and returns the winner's result; unrelated conflicts retry up to eight times, then return 503 with `RETRY_SAVE`. A crash before the write leaves no side effects; a crash or lost response after the write is resolved by retrying the same attempt. If no write happened, a later retry's server receipt time becomes the completion time. Client clocks cannot determine an earlier completion time.

No new collection, transaction, uniqueness index, or replica set is required. Server-generated UUIDs distinguish starts, and the document version acts as the concurrent write gate. Client-supplied IDs are never inserted. Different attempts may legitimately earn different rewards; concurrent completions reload inventory before choosing a reward. All User `save()` calls now use optimistic concurrency, so simultaneous profile edits may receive an existing route's error response and need a retry rather than overwrite newer game data.

Leaderboard ranking is unchanged: one progress entry per profile and date, with the most recently committed distinct completion replacing that day's time. Weekly/all-time totals and sorting are untouched. Replaying an older completion does not replace a newer day's score. Server validation of a solved path is outside this sprint; the existing minimum-duration rule remains.

## Existing data and compatibility

Changes are additive and lazy. No backfill, data deletion, reward reconciliation, or index migration is required. Normally created Mongoose user documents have `__v`; imported/older production records must be audited rather than assumed to have it. Preserve existing versions. Do not strip versions in maintenance scripts. Imported/corrupt users without a non-negative integer `__v` are rejected with 409 `PROFILE_VERSION_REQUIRED` before starting or saving a new completion: Mongoose otherwise omits the version predicate. A model save hook also rejects existing unversioned/invalid-version records on profile saves, so another route cannot accidentally initialize a version and bypass this policy. Maze start/completion return 409 with the code; older profile-write handlers retain their existing 400/500 error envelopes and persist nothing. Registration of new users still initializes `__v` normally. Saved result replay and historical-completion detection remain read-only and work without a version. Any repair of such player data requires an explicit reviewed migration with writers drained; this sprint does not silently initialize versions. No automatic expiry/TTL policy is introduced. An optional persisted `expiresAt`, if present, is enforced for unfinished attempts; existing attempts without it remain playable. Invalid/future start times are rejected.

Old clients may omit `attemptId`: their latest attempt is selected and pinned across internal retries. New saves made this way also get a replayable response. Across separate legacy requests, an intervening start makes this inherently ambiguous: old clients cannot identify a previous attempt. Upgrade the frontend for safe refresh recovery and multi-tab behavior. Historical completed attempts without a response snapshot return 409 `LEGACY_COMPLETED` and never award again; their original reward cannot be reliably reconstructed. Existing reward quantities (including quantities above one and retired catalog IDs) and older progress/attempt records are preserved. New selection excludes any already-present reward key, matching existing rules. Previously duplicated rewards are not removed, quantities are not normalized, and old reward attribution is not guessed. Regression tests insert raw legacy-shaped BSON records to cover these cases.

The legacy `/users/subprofile/:id/progress` write endpoint previously accepted arbitrary client times. It now returns existing saved progress without modifying it, or 409 directing callers to `/maze/complete`. The current client has no callers. Third-party clients relying on that endpoint must adopt server-started completions; this is an intentional compatibility restriction required for server-authoritative leaderboard data.

## Safe Railway deployment sequence (operator instructions only; not executed)

1. **Before approval/cutover:** pin the tested PR commit and current Railway deployment ID for recovery. Confirm CI is green and use a separate staging Railway environment/database with synthetic fixtures for start, completion, replay and old-client requests. The analyzer is offline tooling; do not run the maze/reward seeders or modify the production start command (`npm start`). The server has no build/compilation stage; `npm ci` installs locked dependencies and runtime remains Node 24.
2. **Compatibility gate:** an authorized operator must review a backup and a read-only production inventory of users with missing, null, negative, fractional or otherwise invalid `__v`, old completed attempts without snapshots, and existing reward maps. This task has not queried production. Missing-version records are a deployment blocker for uninterrupted play on those accounts: start/completion fail closed rather than silently rewriting data. If any require repair, approve and test a separate narrowly scoped migration with all writers stopped, backups and before/after checks. Do not globally reset versions or rewrite rewards/progress. Ordinary valid-version users need no migration/index change. Confirm no external writer bypasses version checks and acknowledge the legacy progress-write restriction before proceeding.
3. **Prevent automatic overlap:** Railway's normal replacement/rolling deployment can start a new deployment before all old processes exit; a successful health check alone does not prove a safe cutover. Control auto-deploy for this release, install an upstream maintenance gate for all game/profile writes (and pause any other writers), drain in-flight writes, stop all old Railway deployments/replicas, and verify they are stopped. Then start the pinned new backend behind that gate. If the configured Railway service cannot guarantee this no-overlap sequence, keep traffic gated and arrange a stop/start window rather than do a normal rolling release. No Railway settings are changed by this PR.
4. **Verify before reopening:** confirm every serving replica uses the same new commit and expected existing database binding, with no old deployment still reachable. Validate application health without running test/seed commands against production. Remove the gate only after the compatibility gate is satisfied. Deploy client PR #26 after the entire backend is updated; retain the same API URL and JWT signing configuration so existing sessions survive. Monitor `PROFILE_VERSION_REQUIRED`, `LEGACY_COMPLETED`, save failures and conflict retries without logging player secrets. Verify behavior using synthetic fixtures in staging; production player data is never test data.
5. **Retain recovery data:** preserve response snapshots, attempt IDs and versions indefinitely until an explicitly designed retention policy exists. Attempts and snapshots grow the existing embedded arrays; MongoDB's 16 MiB document limit remains an architectural constraint. Archival or reward reconciliation requires separate player-data review. No TTL/deletion/backfill runs during deployment.

### Rollback

- Prefer rolling the frontend back while keeping this idempotent backend: ID-less clients remain supported with the documented latest-attempt ambiguity. Pending sessionStorage recovery may become unavailable in the old frontend, so keep the new frontend available until pending saves are resolved when practical.
- Once this backend has accepted completions, **do not simply redeploy an older backend**. Old handlers may ignore IDs/snapshots, re-award rewards, change daily time, or discard new fields during a later save. Reverting the frontend does not eliminate delayed requests or pending retries. Reuse the maintenance gate, drain and stop all workers first. Keep start/complete and all unsafe User writes unavailable if only the old backend can run; reopen them only with an idempotency-compatible fix or a separately reviewed recovery plan. There is no safe transparent rollback to pre-idempotency writers while retaining live completions.
- Keep the additive data in place. Do not unset `attemptId`, `result` or `__v`, decrement rewards, rerun seeders, or restore a whole database backup merely to roll application code back: a restore would lose legitimate subsequent player activity. Any data restoration/repair needs explicit approval and reconciliation. New-backend forward fixes should preserve saved snapshots and return the original result.

## Tests

Use Node and a local `mongod` binary:

```sh
MONGOD_BINARY=/absolute/path/to/mongod npm test
```

The combined `npm test` command automatically discovers the unchanged analyzer tests, report-validation tests, and MongoDB completion integration tests. Server CI asserts all three files exist, installs checksum-verified MongoDB 8.0.16, runs the entire suite, checks JavaScript syntax, then retains the CLI smoke checks and deterministic 1,000-seed/10,000-seed report validation. Missing mongod or failing integration setup fails CI; integration tests are never skipped. No shared MongoDB service or production connection is needed.

The integration suite spawns its own mongod on loopback with a temporary data directory and synthetic users, profiles, mazes and rewards; it never consumes `MONGO_URI` or starts the production entrypoint. It covers normal/legacy completion, simultaneous duplicates and distinct attempts, repeated replay after a new start, lost HTTP response after persistence, failure before persistence, invalid/expired/foreign attempts, immutable rewards and leaderboard consistency. Browser refresh and timeout recovery live in the companion client PR. The backend is unbundled JavaScript and has no production build script; syntax-check its application modules in addition to running integration tests.
